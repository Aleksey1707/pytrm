# Распространение транзакции

- **Область.** `pytrm/bases.py` (`_initialize`, `_do`), `share.Propagation`, `share.Settings`.
- **Читать перед.** Правкой `bases.py`; добавлением или изменением правила распространения;
  разбором поведения вложенных блоков `do()`.
- **Словарь.** Плейсхолдеры и модальность — `00-index.md`.

## Семантика семи правил

`_initialize` приводит контекст к состоянию, которого требует правило, и только потом `_do`
открывает транзакцию. Таблица — норма; расхождение кода с ней есть дефект кода.

| Правило | Транзакция в контексте есть | Транзакции нет |
|---|---|---|
| `REQUIRED` | переиспользовать существующую | создать новую |
| `NESTED` | создать вложенную от текущей и положить под тем же ключом | создать новую |
| `MANDATORY` | переиспользовать существующую | `PropagationMandatoryTrmException` |
| `NEVER` | `PropagationNeverTrmException` | выполнить нетранзакционно |
| `NOT_SUPPORTED` | убрать транзакцию из контекста (приостановить) | выполнить нетранзакционно |
| `REQUIRES_NEW` | создать новую, подменив её в контексте | создать новую |
| `SUPPORTS` | переиспользовать существующую | выполнить нетранзакционно |

«Приостановить» и «подменить» означают правку **контекста**, а не транзакции: родительская
транзакция остаётся открытой, её просто не видно внутри блока. Она снова доступна снаружи,
потому что контекст неизменяем и наружный кадр держит свой экземпляр.

Нетранзакционно выполняться MAY только `NEVER`, `NOT_SUPPORTED` и `SUPPORTS`. Для остальных
правил отсутствие транзакции после `_initialize` — дефект, и `_do` MUST бросить
`TransactionNotFoundInContextException`, а не тихо выполнить блок.

## Владение транзакцией

Фиксирует и откатывает транзакцию тот кадр, который её начал. Инвариант:

- `begin` вызывается MUST только когда транзакция в контексте неактивна (`is_active()`
  вернул `False`);
- если транзакция уже активна, блок MUST только выполнить тело и выйти — без `commit`
  и без `rollback`;
- `commit` и `rollback` MUST NOT вызываться из прикладного кода: единственный их вызов —
  внутри `_do`.

Отсюда поведение вложенных `REQUIRED`: внутренний блок ничего не фиксирует, решение
принимает внешний. Если нужна независимая фиксация — это `REQUIRES_NEW`, если частичный
откат — `NESTED`.

```python
# плохо — ручная фиксация внутри блока: внешний кадр потеряет владение
async with trm.do(ctx) as new_ctx:
    session = pytrm.get_native_transaction(new_ctx, "orders")
    await session.commit()

# хорошо — выход из блока без исключения фиксирует сам
async with trm.do(ctx) as new_ctx:
    session = pytrm.get_native_transaction(new_ctx, "orders")
    await session.execute(stmt)
```

## Исключения и `exclude`

Выход из блока без исключения фиксирует изменения; исключение откатывает. Параметр
`exclude` переворачивает решение для перечисленных типов: такое исключение фиксирует
изменения и всё равно пробрасывается наружу.

- `exclude` MUST перечислять только типы, для которых фиксация — часть бизнес-смысла
  (например, доменный отказ, который уже записан в БД); «на всякий случай» это не пишут.
- Исключение MUST пробрасываться в обоих случаях: `_do` не гасит ошибку, он выбирает
  между `commit` и `rollback`.
- Проверка идёт через `isinstance`, значит подкласс перечисленного типа тоже попадает под
  `exclude`. Указывать SHOULD самый узкий тип.

```python
# плохо — гасит всё подряд, откат никогда не произойдёт
async with trm.do(ctx, exclude=(Exception,)) as new_ctx:
    ...

# хорошо — фиксируем только осознанный доменный отказ
async with trm.do(ctx, exclude=(OrderRejected,)) as new_ctx:
    ...
```

## Выбор правила на call site

Правило берётся из настроек и переопределяется параметром `propagation` у `do()`.

- Переопределять правило MUST через `propagation=` или `Settings.with_propagation`;
  пересобирать `Settings` вручную на call site SHOULD NOT — `Settings` — frozen dataclass,
  и `with_propagation` уже даёт корректную копию.
- Ключ настроек (`Settings.key`) MUST оставаться тем же при смене правила: по нему
  транзакция ищется в контексте, и подмена ключа превращает вложенный блок в независимый.

```python
# плохо — ручная пересборка настроек
settings = pytrm.Settings(key=settings.key, propagation=pytrm.Propagation.REQUIRES_NEW)

# хорошо
async with trm.do(ctx, propagation=pytrm.Propagation.REQUIRES_NEW) as new_ctx:
    ...
```

## Вложенные транзакции

`NESTED` зовёт `_create_nested_transaction`, передавая туда **родительскую** транзакцию.
Реализация оборачивает её нативный объект (`unwrap()`) в точку сохранения.

- Реализация, у которой вложенность не поддержана драйвером, MUST бросать
  `NestedTransactionsNotSupportedTrmException`, а не молча открывать обычную транзакцию.
- Вложенная транзакция MUST класться в контекст под тем же ключом: иначе
  `get_native_transaction` внутри блока вернёт родителя.
