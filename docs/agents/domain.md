# Документация домена

Как инженерным скиллам следует читать доменную документацию этого репозитория при исследовании кодовой базы.

## Читай это перед исследованием

- **`CONTEXT.md`** в корне репозитория.
- **`docs/adr/`**: читай ADR, которые касаются области, где предстоит работать.

Если этих файлов нет — **молча продолжай**. Не сообщай об их отсутствии и не предлагай создать их заранее. Скилл `/domain-modeling` (доступный через `/grill-with-docs` и `/improve-codebase-architecture`) создаёт их лениво, когда термины или решения действительно фиксируются.

## Структура файлов

Одноконтекстный репозиторий (наш случай):

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-context-immutability.md
│   └── 0002-sqlalchemy-session-scope.md
└── pytrm/
```

Если репозиторий когда-нибудь разъедется на несколько контекстов, признаком станет `CONTEXT-MAP.md` в корне: он указывает на отдельный `CONTEXT.md` для каждого контекста, а решения, специфичные для контекста, живут в `<context>/docs/adr/`. Сейчас такого разделения нет.

## Используй словарь глоссария

Когда в твоём выводе фигурирует доменное понятие (в заголовке задачи, предложении по рефакторингу, гипотезе, имени теста), используй термин в том виде, в каком он определён в `CONTEXT.md`. Не сползай на синонимы, которых глоссарий явно избегает.

Если нужного понятия в глоссарии ещё нет — это сигнал: либо ты изобретаешь язык, которым проект не пользуется (стоит пересмотреть), либо есть реальный пробел (зафиксируй его для `/domain-modeling`).

## Сообщай о конфликтах с ADR

Если твой вывод противоречит существующему ADR, проговори это явно, а не переопределяй молча:

> _Противоречит ADR-0007 (неизменяемость контекста), но пересмотреть стоит, потому что…_
